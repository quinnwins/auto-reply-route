# Follow-up selection in T3 Code

Apply this in T3 Code, including to a worker producing a deliverable when its assignment permits an independent reviewer. Reviewers finish their assigned review without starting another reviewer. Follow the caller's latest instructions, including stop, scope, work-alone requests and limits on child agents. Leave a named workflow in control.

Choose one path for the user's request. A fresh review of the requested artifact and its source evidence covers the handoff that summarizes the verdict. Recheck only a material change to the artifact, evidence or claims.

When project QA requires a fresh reviewer to exercise a changed user flow, use a fresh session from the same model family by default and save `REVIEW.md` before merge. Keep the normal QA handoff. Visual critique cannot satisfy this behavior check. The hands-on review covers the completion review of the same final change. Recheck affected behavior after further edits.

- Answer a simple question or perform a purely mechanical change directly.
- For routine visual design or polish, choose Direct. The original builder uses the rubric from the brief (or its audience and task) on renders at the target sizes (desktop and phone for responsive work), names the screen, visible weakness and reader impact, revises once if needed, and verifies. A self-score is optional. In a top-level T3 user chat choosing among finished directions for a flagship screen or redesign, use the council skill’s blind finished-design comparison directly. For a requested second opinion or one material visual question still unresolved, send the brief, renders and question to one read-only reviewer from a different model family when available. The original builder decides and edits. Count visual advice only when the reviewer saw the renders and cites a visible detail tied to the brief. Disclose missing image access. These design paths do not arm a Stop review.
- For a large change with an open decision that would materially alter the scope or approach, use council before choosing a plan or implementing it. For example, two credible redesigns would change different user flows. Only the top-level interactive T3 agent with `delegate_task` takes this path. Read the council skill at `~/.claude/skills/council/SKILL.md` and follow its planning rounds with the configured seats. Use the result for the authorized work. This choice needs no Stop review or adaptive continuation. A settled rollout, a large mechanical edit, or a discussion about council routing does not trigger it.
- For a substantive deliverable that requires checking records or using a feature, select one independent review, even for short output. As the first available tool action run `python3 ~/.grok/hooks/grok_followup.py review`, then complete the task. If the command confirms the selection, Grok's Stop hook will ask for the review. If it reports hooks unavailable in this workspace, complete the deliverable and start the permitted read-only reviewer in this turn, before delivering the final answer. Use one fresh native Grok subagent, give it the original request and the minimum relevant evidence, and wait. Fix and verify any concrete in-scope omission. If the user asked to work alone or another workflow already reviews this result, finish normally.
- For sustained work whose next action depends on findings, choose an adaptive workflow. Do and verify what you can now. If one specific authorized core step still needs a continuation, run `python3 ~/.grok/hooks/grok_followup.py next` immediately before stopping. Grok can continue in this same thread up to four times. Stop when verified, genuinely blocked, interrupted, or at the limit. If native continuation is unavailable, do remaining authorized work now and report any real blocker.

These instructions give no extra permissions for tools or external actions. If an independent reviewer is unavailable, report that limitation.
